# BuckParts Executive Evolution Gate v1

**Status:** Standing judgment standard only (docs).  
**Authority:** Subordinate to `docs/BuckParts-CONSTITUTION.md` and the Executive Operating System (`AGENTS.md` + current stopping point in `docs/BuckParts-HQ-HANDOFF.md`). Does **not** authorize mutation, NBA, Dispatch, Daily Operator, Command Center steering, scoring, weighting, new stores, or new engines.  
**Question this gate answers:** *What evidence must exist before a proposed Executive capability may claim a named permission in a named scope?*  
**Burden of proof:** On the **proposer of the authority claim**. Silence, elegance, roadmap pressure, or reviewer convenience do not pass the gate.

---

## 0. Surviving invariant (mandatory)

**Existence, evidence, permission, scope, and availability must not be represented as one state.**

Rejected model: one object progressing through maturity labels (“temporary → graduate → permanent → retire”) as if those words meant the same thing.

Correct model: a capability may **persist** while its **authority assignments** change by evidence, scope, consequence, dependencies, and constitutional limits. The capability itself is **not promoted**.

A capability may simultaneously be, for example:

- supported by evidence in one scope,
- experimental / lightly evidenced in another,
- advisory in one decision class,
- bounded-execution authorized in another,
- dormant because a dependency is unavailable,
- protected from casual deletion,
- historically retained after operational use ends.

Those are **illustrative co-existing facts**, not a required seven-part ontology. Do not invent a registry or lifecycle engine to store them.

---

## 1. Purpose

BuckParts must not accumulate Executive machinery that claims authority without evidence, or that treats “merged / tested / exists” as permission.

This document is the **smallest durable gate** for **authority claims** about Executive capabilities. It invents **no architecture**. It scores **nothing**. It stores **nothing**. It only states what must be proven in writing before a **named permission in a named scope** is claimed.

Useful questions this gate still forces (without collapsing them into one maturity bit):

| Concern | Gate asks… | Must not be confused with… |
|---------|------------|----------------------------|
| Existence | Is a capability instantiated in-repo? | Permission to steer or mutate |
| Evidence | What observation / learning is PROVEN? | Merge or test green |
| Permission | What may it do (advisory vs bounded execution vs none)? | “Permanent” as a vibe |
| Scope | Where does that permission apply? | Global organ status |
| Protection | What deletion cost / retention is claimed? | Authority |
| Availability | Can it run now (deps up)? | Evidence or permission |
| Dependencies | What must be present for a claim? | Existence alone |

## 2. Hard rules (derived)

From Constitution + Operating System only:

1. **Systems are means** — process earns continued operating cost only through customer value or decision quality (§3 Customer Reality).
2. **Evidence precedes authority** — discovery is not closure; instantiation is not permission (§7, §12).
3. **UNKNOWN beats invention** — missing proof is fail-closed, not a soft pass (§5, §6).
4. **One proving ground / one lane** — expansion for its own sake is prohibited (§8; OS one-lane rule; HQ “no Executive OS expansion for its own sake”).
5. **Expose → measure → correct** — authority claims follow reality contact, not design completeness (HQ execution loop).
6. **No steering from unproven sensors** — sensory or drafting surfaces do not become NBA/Dispatch/Daily authority by merge alone (HQ Drift Watch F2/F4; OS founder gates).
7. **Verification ≠ customer proof** — tests/validators prove honesty of claims, not homeowner outcomes (HQ Drift Watch F6; HyperAgent rule).
8. **Removal / retention stay explicit** — prefer reversible attachments; deletion protection is not an authority grant (Trust Hierarchy §4 item 4).
9. **No single-state collapse** — never encode existence + evidence + permission + scope + availability as one label.

**Default verdict on authority claims:** `PARK` or `REJECT`. Non-zero Executive permission is never the default. Instantiation with **zero** Executive permission may still be allowed when honestly labeled.

## 3. What counts as an “Executive capability” (for this gate)

Any proposed capability that claims to be part of the Executive Operating System surface, including but not limited to:

- a new sensory path, scoreboard sibling, or Command Center field family
- a new drafting discipline, registry, queue, or decision artifact type
- a new Runner / digest / dashboard attach that changes what founders are told to do
- a new “learning,” “prior,” “weight,” “NBA,” or “dispatch” consumer

**Gate applies when any of these are claimed:**

- a new **permission** (advisory, steering, mutation, NBA, Dispatch, Daily, bounded execution),
- a widened **scope** for an existing permission,
- **deletion protection** that blocks removing unused machinery without evidence,
- “standing” / “earned” language that implies authority from existence alone.

**Gate does not block mere instantiation** when the packet states **permission = none** (or advisory-only labels with all authority locks false) and does not claim steering/mutation.

If unsure, treat it as an authority-claim subject and require the packet.

## 4. The Gate (eight fields — all required for an authority claim)

Every proposal that claims a **named permission in a named scope** must answer all eight fields in writing.  
Empty, vague, aspirational, or `UNKNOWN` answers ⇒ **gate FAIL** for that authority claim.

| # | Field | What must be proven | Fail-closed if… |
|---|--------|---------------------|-----------------|
| 1 | **Observation gained** | Exact new observation the capability makes possible that did not already exist as PROVEN repo truth. Name the signal and where it is read. | Observation is restated metrics, vanity counters, or “better visibility” without a new checkable fact. |
| 2 | **External outcome expected** | The customer or reality outcome this observation is *for* (wrong-part prevention, honest no-buy, clearer comparison, reversible correction). Internal elegance is not an outcome (§3). | Outcome is internal-only (dashboard beauty, coverage theater, agent convenience) or monetization-first (§4). |
| 3 | **Existing capability overlap** | Named existing capabilities/contracts this overlaps; why those cannot absorb the work; what will *not* be duplicated. | Overlap is denied without naming siblings, or proposes a parallel store/engine for the same class of fact. |
| 4 | **Constitutional necessity** | Which Constitution obligation fails if this **authority claim** is withheld (cite §). Prefer harm reduction, honest UNKNOWN, evidence-before-authority, fail-closed automation. | Necessity is speed, completeness, roadmap symmetry, or “Phase N expects a sibling.” Existence alone is not necessity. |
| 5 | **Measurable learning increase** | What decision changes after the capability sees reality — and how learning is checked without a score/weight engine. Prefer: fewer repeated founder questions, fewer false certainties, clearer PARK/REJECT, honest UNKNOWN rates. | “Learning” means a score, rank, weight, or auto-NBA. Or no before/after decision difference is named. |
| 6 | **Failure mode** | How the capability fails safely: what stays UNKNOWN; what it must never steer; what false proof it must refuse (no false zero; no invented precedent; no buy CTA from soft confidence). | Failure mode is omitted, or failure would quietly grant authority / invent certainty. |
| 7 | **Removal / retention test** | Exact test: *If we delete or stop invoking this capability tomorrow, what customer harm or decision-quality loss is PROVEN?* Separately state deletion cost and whether historical retention is needed. Deletion protection ≠ permission. | Removal would strand authority, or “keep forever” is claimed without proven loss if removed. |
| 8 | **Authority-assignment criteria** | Finite, checkable conditions for the **named permission + named scope** — including reality exposure (not tests alone), dependencies/availability, non-claims outside scope, and founder acknowledgment. | Criteria are vibes (“feels useful”), test pass alone, merge-as-proof, or a single “promoted/permanent” bit. |

### Verdict labels (no scores — apply to the **authority claim**, not to existence)

| Verdict | Meaning |
|---------|---------|
| `REJECT` | Fails constitutional necessity, invents authority, or creates unnecessary machinery. |
| `PARK` | Evidence incomplete for the requested permission/scope; do not grant that authority claim. Instantiation may still be declined or allowed separately if labeled zero-authority. |
| `INSTANTIATED_ZERO_AUTHORITY` | Capability may exist in-repo (tested, documented) with **no** Executive permission (all steering/mutation/NBA/Dispatch/Daily locks false). Existence ≠ earned authority. |
| `AUTHORITY_CLAIM_CANDIDATE` | All eight fields answered with checkable claims for a **named permission + scope**; still requires founder decision. Does **not** auto-apply or auto-steer. |

There is no numeric score. There is no weighted rubric. Pass/fail is qualitative and fail-closed.

**Forbidden single-state labels (do not use as organ maturity):** `temporary`, `graduation`, `promotion`, `permanent` (as capability lifecycle), `retirement` (as a single end-state that erases history/evidence distinctions). Prefer explicit sentences about existence, evidence, permission, scope, and availability.

## 5. Existence vs permission (OS alignment)

| Fact | Allowed when… | Must not imply… |
|------|----------------|-----------------|
| **Proposal** | Written gate packet for any non-zero permission/scope claim | That the capability “already has” authority |
| **Instantiation** | Code/docs/tests exist; packet states permission = none / advisory labels only | Steering, mutation, NBA, Dispatch, or “earned permanence” |
| **Authority assignment** | Founder-accepted claim after **AUTHORITY_CLAIM_CANDIDATE** + reality exposure for that scope | That tests, merge, or HQ mention assigned permission |
| **Availability / dormant** | Dependencies missing ⇒ capability may be present but not runnable | That dormancy clears or grants permission |
| **Retention after use ends** | Historical artifacts kept for audit / precedent | Ongoing operational authority |

HQ execution philosophy remains binding in spirit: prefer **one** capability exposed to reality → measure → correct → repeat — without treating “one permanent capability” as a maturity promotion bit. Prefer: one authority claim at a time, honestly scoped.

---

## 6. Anti-accumulation clauses

1. **Burden on the claim** — reviewers need only find one unanswered field or one invented claim to withhold the requested permission/scope.
2. **No twin capabilities** — if field 3 shows an existing capability can absorb the observation, extend that capability; do not mint a peer.
3. **No scoring theater** — any proposal whose “learning” requires a weight engine, priority score, or auto-rank fails field 5 unless and until Constitution/OS are amended to allow it.
4. **No regime shift by attach** — wiring a sensor into NBA/Dispatch/Daily is a **new authority claim** and must clear this gate again (HQ F2/F4).
5. **Map must not eat territory** — Command Center / digest fields do not assign permission by display alone (HQ F4).
6. **Precedent discipline** — when arguing from past capabilities, cite closed precedent honestly or state `NONE` / `UNKNOWN` (Precedent Clause posture); do not invent institutional memory.
7. **No promotion language** — do not say a capability was “graduated,” “promoted,” or “made permanent.” Say which **permission** was assigned in which **scope**, on what **evidence**.

```text
EXECUTIVE EVOLUTION GATE v1 — AUTHORITY CLAIM PACKET
proposer:
capability_name:
existence_claim: not_instantiated | instantiated
evidence_summary: PROVEN | INFERRED | UNKNOWN (one line)
permission_claimed: none | advisory_labels_only | bounded_execution | steering | mutation | other:
scope_claimed:
availability_claim: available | dormant_dependency | unknown
dependencies:
deletion_protection_claimed: none | soft | hard (justify in field 7)
date:

1. Observation gained:
2. External outcome expected:
3. Existing capability overlap:
4. Constitutional necessity (cite §) for this permission/scope:
5. Measurable learning increase (no score/weight engine):
6. Failure mode (UNKNOWN / non-steering / refusals):
7. Removal / retention test (harm if deleted + how to delete; protection ≠ permission):
8. Authority-assignment criteria (named permission + scope; reality exposure + founder ack):

authority_locks_claimed:
  read_only:
  data_mutation:
  mutation_authorized:
  steering_authority:
  nba_authority:
  dispatch_authority:

verdict_requested: REJECT | PARK | INSTANTIATED_ZERO_AUTHORITY | AUTHORITY_CLAIM_CANDIDATE
```

Incomplete packets are `PARK` or `REJECT` by default for any non-zero permission claim.
